# The inverse and hyperbolic unary family on the VC4 QPUs

This is the measurement record for the nine ONNX operators `Asin`, `Acos`,
`Atan`, `Atanh`, `Asinh`, `Acosh`, `Sinh`, `Cosh` and `Tan`.  It is the
companion of `ONNX.md` §12 (the forward transcendental family: `Exp`, `Log`,
`Sqrt`, `Reciprocal`, `Tanh`, `Erf`, `Sin`, `Cos`) and follows the same
pattern, in the same order: a bit-exact ALU emulator for the body, then a
16-lane hardware probe, then the five shapes, then the ONNX graphs, and only
then registration.

Everything below was measured on this board with the core clock pinned at its
stock 400 MHz (`core_freq=400`, `core_freq_min=400`), one client at a time
through `vc4d` (no `flock`).

## 2. Per-operator record

One QPU kernel per operator (`infer/tools/kops.py`, generated by
`kgen.build_ew`), at **nvec=4** — the 16-vector copy of every one of these
bodies is 28-40 KiB, and the family already proves that the 4-vector group
path is the correct one for long bodies (`ONNX.md` §12.3).  Sizes are the
generated blob words/bytes for one launch shape.

| op | method | domain enforced | worst measured | body |
|---|---|---|---|---|
| `Asin` | two-branch, one polynomial: `a + a³Q(a²)` for `a=|x|<=0.5`; `pi/2 - 2(s + s³Q(s²))`, `s=sqrt((1-a)/2)` above | `-1 <= x <= 1` | abs 2.9e-7 | 1351 w / 10.8 KB |
| `Acos` | `pi/2 - Asin(x)` (one extra `fsub`) | `-1 <= x <= 1` | abs 2.9e-7 | 1363 w / 10.9 KB |
| `Atan` | `r = min(|x|, 1/|x|)`, degree-13 odd polynomial on `r²∈[0,1]`, then `pi/2 - atan(r)` for `|x|>1` | every finite `x` | abs 4.6e-7 | 1029 w / 8.2 KB |
| `Atanh` | `ln((1+a)/(1-a))/2` through the verified log core, sign restored | `-1 < x < 1` | abs 1.7e-6 (rel 1.9e-7) | 1469 w / 11.8 KB |
| `Asinh` | `ln(a + sqrt(a²+1))` through the log core; `ln(a)+ln2` above `2^63` | every finite `x` | abs 1.6e-6 (rel 1.7e-7) | 1987 w / 15.9 KB |
| `Acosh` | `ln(x + sqrt((x-1)(x+1)))` through the log core; `ln(x)+ln2` above `2^63` | `x >= 1` | abs 1.6e-6 (rel 1.7e-7) | 1989 w / 15.9 KB |
| `Sinh` | `sign(x)*(t - 1/t)/2`, `t = e^{|x|}` (exp core + Newton reciprocal) | `-88 <= x <= 88` | rel 9.3e-6 | 1023 w / 8.2 KB |
| `Cosh` | `(t + 1/t)/2`, `t = e^{|x|}` | `-88 <= x <= 88` | rel 9.6e-6 | 1001 w / 8.0 KB |
| `Tan` | Cody-Waite `q = round(2x/pi)`; degree-13 odd polynomial for `tan(r)`; `-1/tan(r)` for odd `q` | `|x| <= 1e5` and `|cos(x)| >= 0.05` | abs 4.9e-6 (rel 3.5e-5) | 1075 w / 8.6 KB |

"Worst measured" is the largest `|got - ref|` (and relative error) over the
five shapes of `check_uops_gpu.py` (`1, 16, 17, 256, 4096`), random data
inside the domain plus a 16-value boundary vector, against a float64
reference.  The 1e-4 + 1e-4·max(|ref|,1) tolerance is met with margin in every
case; the widest use of it is `Sinh`/`Cosh` at 10% (`rel 9.4e-6 / 1e-4`).

`Asinh` and `Acosh` are the largest bodies in the kernel family (15.9 KB).
The 16-vector form would be 28-40 KiB; the existing `Mish` body is 16.6 KB and
has been running since the unary commit, so 16 KiB is not a hard slot on this
board, but the 4-vector path is the verified one and is used.

## 3. How each body is built

### 3.1 The polynomial cores (`Asin`, `Acos`, `Tan`)

Every coefficient is a float64 minimax fit (weighted least squares on 6000
Chebyshev nodes, 80 exchange iterations) rounded to fp32, and the fit error is
re-checked *after* rounding:

| core | form | argument | max abs error of the fit |
|---|---|---|---|
| `asin` | `u + u³Q(u²)`, 5 coefficients | `u ∈ [0, 0.5]` | 8.2e-9 |
| `atan` | `r + r³P(r²)`, 7 coefficients | `r ∈ [0, 1]` | 4.3e-7 |
| `tan` | `r + r³T(r²)`, 6 coefficients | `r ∈ [0, pi/4]` | 5.8e-8 |

`Asin` uses fdlibm's two-branch shape with **one** polynomial: `Q` is fitted on
`[0, 0.25]` in `t = u²`, and both halves reduce to that interval, so the
branch only picks the argument (`a` or `s = sqrt((1-a)/2)`) and the final
`pi/2 - 2p`.  That is what keeps `asin(1-2^-24)` accurate: `1-a` is exact
there (Sterbenz), `2^-12` structure of the answer comes out of the `sqrt`, and
no subtraction of two nearly equal `O(1)` numbers is ever formed.

`Acos` is `pi/2 - Asin(x)` and *does* pay that cancellation: `acos(x)` for
`x -> 1` is `pi/2 - (pi/2 - eps)` and one ulp of `pi/2` survives
(`acos(1)` returns `2^-25` instead of 0, `acos(-1)` returns `pi - 1 ulp`).
The absolute cost is 1.2e-7 against a 1.2e-4 tolerance, i.e. it is measured,
not assumed: the boundary rows of the table above are exactly those points.

`Tan` computes `tan(r)` **directly** rather than `sin(r)/cos(r)`.  That is the
whole point of the design: near a pole `tan(x) = -1/tan(r)` with `r` small, and
`tan(r) = r(1 + r²/3 + ...)` carries its *relative* accuracy, whereas a ratio
of two `O(1)` values would lose it.

### 3.2 The log-based bodies (`Asinh`, `Acosh`, `Atanh`)

`b_log`'s verified body was factored into `core_ln` (the emitted words for
`Log` are byte-identical, checked by regenerating the blob before and after:
1031 words both times) and reused.  The three callers feed it arguments that
keep it accurate:

* `Atanh`: `(1+a)/(1-a)`; `1-a` is exact for `a ∈ [0.5, 1]`, so `atanh(1-2^-24)`
  is accurate, and near 0 the `(m-1)/(m+1)` series has an absolute error of one
  ulp of 1 (~6e-8).
* `Asinh`: `a + sqrt(a²+1)`; the `+1` is harmless and `sqrt` comes from the
  verified Newton `1/sqrt` core.
* `Acosh`: `x + sqrt((x-1)(x+1))` — factored so `x²-1` never cancels — with
  `x-1` exact near 1.

Above `2^63` all three switch to `ln(a) + ln2` (one `and`, one `fadd`) because
`a²` would overflow; the truncation error of that switch is `1/(4a²)`.

The three values that a log core cannot express are handled explicitly in the
body: `|a| >= inf` selects `+-inf`, `a` NaN selects NaN, and `x == 0` forces an
exact signed zero (otherwise the reciprocal core's ~6e-8 residue would show).
Note `core_ln` uses the 4-term series for these three ops (the dropped `u^9`
term is 1.5e-9 at the largest series argument) because their constant list
plus the 5-term log does not fit the B register pool (see §5).

### 3.3 The exp-based bodies (`Sinh`, `Cosh`)

`t = e^{|x|}` from the verified exp core, then `(t -+ 1/t)/2`.  Two details:

* the reciprocal's bit-trick seed (`0x7EF311C3 - bits(d)`) is only defined for
  `d < 2^126`, and `e^{88}` is 1.6e38 = 2^127.  The input is therefore clamped
  to `2^125` first, where `1/t = 2^-125` is still a *normal* number: no
  denormal is ever formed, and the term is 1e-38 against a 1e38 result.
* `x = +-0` is forced to the exact signed zero (sinh) and to exactly 1.0
  (cosh); the reciprocal core's residue would otherwise give `cosh(0) =
  0.99999994`.

## 4. Special values, measured bit-for-bit

Read back from the QPU as raw words (the FPU has no signed-zero arithmetic, so
these are the cases that need a deliberate instruction):

| input | `Asin` | `Acos` | `Atan` | `Atanh` | `Asinh` | `Sinh` | `Cosh` | `Tan` |
|---|---|---|---|---|---|---|---|---|
| `+0` | `+0` | `pi/2` | `+0` | `+0` | `+0` | `+0` | `1.0` | `+0` |
| `-0` | `-0` | `pi/2` | `-0` | `-0` | `-0` | `-0` | `1.0` | `+0` (see below) |
| `+-inf` | refused | refused | refused | refused | refused | refused | refused | refused |
| `nan` | refused | refused | refused | refused | refused | refused | refused | refused |
| `1` | `pi/2 - 1 ulp` | `2^-25` | `pi/4 - 1e-7` | refused (abs(x) >= 1) | — | — | — | — |
| `-1` | `-pi/2 + 1 ulp` | `pi - 1 ulp` | `-pi/4 + 1e-7` | refused | — | — | — | — |
| `1e-30` | `1e-30` | `pi/2` | `1e-30` | `1e-30` | `-6e-8` (§3.2) | `1e-30` | `1.0` | `1e-30` |

`Acosh(1)` is exactly 0.  `Tan(-0)` returns `+0`: `-0 - (-0*pi/2) = +0`
in the reduction, so the sign of zero is not preserved by the reduction while
every other argument keeps `tan`'s odd symmetry (`tan(-x) = -tan(x)` is
exact-to-tolerance everywhere else).  No ONNX consumer distinguishes `+0` from
`-0`, and the tolerance test cannot; it is recorded here rather than papered
over.

Non-finite operands are refused by the *executor*, not answered: `asinh(inf)`
would be well defined but the log core clamps at 88.7, so the handler refuses
it by name instead of returning a plausible-looking number (the rule `Log`,
`Sqrt` and `Sin` already follow).  `Sinh`/`Cosh` need the same refusal at
`|x| > 88`, where `e^{|x|}` overflows.

## 5. Register and constant budget (why nvec=4 and why 21 constants)

`build_ew`'s harness makes B0-B20, B26 and (for an op with fewer than two
parameters) B30/B31 available to a unary body, minus **B8**, which always holds
the b operand.  That is 23 constant slots.  A long log body needs 8 A-file
temps *and* six live temps inside `core_ln`, so the bodies here keep their
constant list at 21 or less (`Asinh` is exactly 21: 12 for the log core, 3 for
the `1/sqrt` core, 6 for the exponent/branch/zero masks).  `Asinh` and `Acosh`
release their argument and square-root temps across `core_ln` for the same
reason; the emulator is what caught it (the generator raised `pop from empty
list` rather than emitting a body that reads a stale register).

Small immediates are only used in the b slot (`e.opi`, values 0..31), per
`NUMERICS.md` §1.

## 6. Verification sequence and what it caught

All commands run with the in-tree build and a fresh kernel cache:
`PYTHONPATH=infer/python VC4INFER_LIB=infer/build/libvc4infer.so
VC4INFER_KGEN=infer/python/vc4infer/kgen/kgen.py VC4INFER_DAEMON=1`.

1. **Offline, body level** — `infer/tests/check_uops_emu.py` (the bit-exact
   ALU model: truncation, denormal flush) over two 16-lane vectors per op,
   including the branch points `+-0.5`, `+-1`, `+-1e5`, `1e30` and the
   domains' edges: **0 mismatches** for all 35 shipped bodies.
2. **Offline, whole kernel** — `infer/tests/emu_kernel.py 4` (harness
   prologue, uniform port, TMU queue, every per-vector body, the store
   registers): **0 mismatches**.
3. **Hardware, 16 lanes** — the first launch is one vector (`n=1`), then the
   exact 4-vector group (`16`), then the padded tail (`17`), another group
   (`256`) and the multi-launch shape (`4096`):
   `infer/tests/check_uops_gpu.py asin acos atan atanh asinh acosh sinh cosh
   tan` → **0 mismatches over 39,474 elements / 45 runs**.
4. **Hardware, whole family (regression)** — the same script with no `--only`:
   **0 mismatches over 144,738 elements / 165 runs** (26 kernel ops x 5
   shapes), which also re-verifies `Exp`/`Log`/`Erf`/`Sin`/`Cos` after the
   `core_ln` refactor.
5. **ONNX graphs** — `infer/tests/check_onnx_unary.py`: one graph per op at
   `1x3x8x8`, `2x5x7x3` and `1x1x1x1`, random data in the domain plus a
   boundary vector, compared with `onnx.reference`: **0 mismatches over 3,627
   elements / 27 graphs** for the nine, and **14,105 elements / 105 graphs**
   for the whole unary family.
6. **Refusals** — `infer/tests/check_unary_domains.py` feeds one out-of-domain
   value per op through the real executor and requires a *named* refusal, then
   runs the value just inside the boundary: **0 failures** (9 refusals, 5
   inside-boundary answers).
7. **The sweep** — `infer/tools/op_matrix.py --only <the nine> --stage all`:
   **9/9 `vc4`, 0 refused, 0 mismatch**.
8. `REPS=1 ./run_tests.sh` green (see §8).

Three real defects were found this way; each is now a rule in the code:

* **The polynomial coefficients were emitted in the wrong order.** The fit
  returns highest-power first (`np.vander` column order) and the Horner loop
  starts from the highest, so `AT0` had to be the *constant* term.  The
  symptom was a uniform 3-12% error in `asin`/`acos`/`atan`/`tan` — visible in
  the emulator, never on the board.
* **The Newton reciprocal's seed only covers `d < 2^126`.** `Sinh`/`Cosh` of
  `+-88` produced NaN (the seed's exponent borrows into the sign bit and the
  iteration diverges).  Fixed by clamping the reciprocal's input at `2^125`
  (§3.3); the offline harness flagged it at the top of the domain, which is
  where `check_uops_gpu`'s edge vector puts `+-88`.
* **A released temp was reused for the NaN clone.** After `core_ln`,
  `Asinh`'s log-argument register was returned to the pool and then
  re-allocated as `a`, while the non-finite block still wrote the `NAN`
  constant into the old `u`.  That clobbered `a`, so the "x == 0" mask read
  NaN and the exact-zero path never fired (and `asinh(nan)` answered `+inf`).
  `keep_sel` reads its `a_true` operand, so the constant registers are now
  used directly and no clone is needed.

## 7. What is still refused, with the exact limit

| op | refused when | why |
|---|---|---|
| `Asin`, `Acos` | `x` outside `[-1, 1]` | real part ends at `+-1`; the polynomial is only fitted/verified there |
| `Atanh` | `|x| >= 1` | `atanh(+-1) = +-inf`; the kernel's log form reaches 44.4 there, so it is refused rather than answered |
| `Acosh` | `x < 1` | the body is `ln(x+sqrt((x-1)(x+1)))`; below 1 the sqrt is of a negative number |
| `Asinh`, `Atan` | non-finite `x` | the log core clamps at 88.7 and `atan`'s fold is only verified for finite input; `asinh(+-inf)` would be `+-inf` but is refused by the same uniform rule |
| `Sinh`, `Cosh` | `|x| > 88` (and non-finite) | `e^{88} = 1.65e38`; past that `t` overflows and `1/t` flushes, so the body would return a finite lie instead of `+-inf` |
| `Tan` | `|x| > 1e5` | the Cody-Waite reduction is the `Sin`/`Cos` one, verified to 1e5 |
| `Tan` | `|cos(x)| < 0.05` | see below |

The `Tan` limit is the only non-interval domain in the family and it is worth
stating precisely.  The answer near a pole is `-1/tan(r)` with `r = x - q*pi/2`
small, so its *relative* error is the relative error of `r`.  The reduction's
absolute error in `r` comes from `q*PIO2_MID` (the `q*PIO2_HI` product is exact
by construction: 8 significant bits times `q <= 63662`), i.e.
`delta_r <= |x| * 4.8e-4 * 2^-24 / (pi/2) ~= 1.8e-6` at `|x| = 1e5`, and it
scales with `|x|`.  Requiring `delta_r/|r| <= 1e-4` gives `|r| >= 0.018` at
`|x| = 1e5`; the implemented rule `|cos(x)| >= 0.05` is that bound rounded up
and made uniform (`|cos| ~ |r|` near a pole).

Measured at the boundary (72 arguments of the form `m*pi/2 +- r` for
`m` in 1..63662, `|r|` between 0.05 and 0.3): the worst element uses **1% of
the tolerance** (max `err/tol` 0.009), and in the near-pole subset
(`|tan| > 5`) the maximum relative error is **2e-7**.  Over the whole
`check_uops_gpu` domain the worst absolute error is 4.9e-6 and the worst
relative error 3.5e-5 (at a point where `|tan|` is small, so the absolute
error is what matters).  For `|x| <= 3`, where the reduction error is ~3e-11,
the kernel is accurate to ~1e-9 relative even within 1e-6 of a pole; the
0.05 rule is deliberately conservative and uniform because it must also hold
at `|x| = 1e5`.

## 8. Registration and the suite

Engine (three files, all additive):

* `infer/include/vc4infer.h` — nine `vc4_uop` values appended after
  `VC4_UOP_MISH`, so no existing op's code moves;
* `infer/src/vc4_gen.c` — `uop_name()` cases and the `uop_nvec()` list (all
  nine are 4-vector bodies);
* `infer/python/vc4infer/_binding.py` — the mirrored enum, `range(36)`.

ONNX dispatch is registered in `infer/python/vc4infer/_dispatch_extra.py`
(one `Trig` handler, the module's documented extension point) rather than in
`_onnxrun.py`; `coverage.py` carries the per-op note that `vc4infer nodes`
prints.  For a graph containing all nine, `vc4infer nodes` reports
`18 nodes: 18 supported, 0 unsupported` and 18 `vc4` (the nine ops plus the
nine `Clip`s the test graph uses to clamp its inputs), with the implementation
text naming the kernel and its limit.

`REPS=1 ./run_tests.sh` (daemon backend): green.  The Python checks above are
not part of that shell suite; they are run explicitly, as in §6.
