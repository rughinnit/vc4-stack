# VC4 training path — results (2026-11-19)

First backward kernels plus a toy trainer, everything that computes on the
QPUs.  Board: Raspberry Pi 3B, kernel 6.18.50, stock clocks.  The clock was
sampled every 50 ms during every measurement below (`vcgencmd measure_clock
core`): the reported runs held **400 MHz** (median and minimum 400 during the
trainer runs; the whole-suite stress run later droops to 250–275 MHz, which is
why each number here has its own clock record).

New tree: `~/work/train` (copy of `engine-fast2`).  The original
`engine-fast2` is untouched.

## What was added

QPU kernels (generated by `tools/kgen.py`, cached blobs in `kcache/`):

| op | how | constraints |
|---|---|---|
| `transpose` | the asm3 packer (VDR + vertical VDW) with the VDW destination stride set to the output row pitch; per-k-block/per-row-block strides place the 16x16 tiles | rows, cols % 16 == 0; cols*4 <= 8191 |
| `matmul_bt` (C = A·Bᵀ) | the packer on B (it already transposes 16 rows into k-major) + the asm3 GEMM with `bmode=1`; A is packed the usual way | M, N, K % 16 == 0 |
| `relu_bwd` | elementwise bit mask: `relu(x)` then `(bits-1)>>31` gives all-ones/0, product is a bit copy | bit-exact, any n (256-rounded internally) |
| `rsqrt` | bit-trick seed + 4 Newton steps, no division | rel err < 1e-5 (measured 8.8e-8) |
| `softmax_ce_bwd` | fused row kernel: rotate+fmax max, degree-5 2^f polynomial exp, rotate+fadd sum, bit-trick+3 Newton 1/S, `(p-onehot)/B`, `loss = (max-z_y)+ln2·log2(S)` (degree-6 log2 poly), `argmax==label`; one 8-row group per QPU | rows % 8 == 0, exactly 16 padded columns |
| `softmax` | the p intermediate of the same kernel (registry entry) | same |

Wrappers/API in `src/vc4_train.c`, `src/vc4_ew.c`, `include/vc4infer.h`;
registry updated in `src/vc4_api.c`.  No new GEMM math: `transpose` and
`matmul_bt` are the already-verified packer/GEMM with different addressing.

Bug found and fixed in the shared engine while doing this: the asm10 pack
kernel was cached under a name that did not include the row-block count, so a
second shape with the same K could demand more QPUs than the cached blob was
registered for.  The blob itself is nqpu-independent, so it is now registered
for the maximum (4) and reused.

## Gradient checks (finite differences; CPU = checker only)

`tests/test_grad.c`.  Every forward value in a finite difference is a QPU
result; every analytic gradient is a QPU kernel result.  Central differences,
L = 0.5·ΣC² (quadratic, so h = 0.1 is exact up to the fp32 forward), ReLU/CE
with h = 0.02.  The QPU FPU truncates and there is no FMA, so agreement is
reported, not bit equality.

| check | n | relative L2 | max per-element rel | max abs |
|---|---|---|---|---|
| dA = dC·Bᵀ, 16³ | 256 | 7.5e-07 | 3.1e-05 | 2.6e-05 |
| dB = Aᵀ·dC, 16³ | 256 | 6.8e-07 | 1.8e-04 | 8.7e-06 |
| dA, 32×32×16 | 512 | 9.6e-07 | 2.3e-04 | 4.5e-05 |
| dB, 32×32×16 | 512 | 7.7e-07 | 3.1e-04 | 2.0e-05 |
| relu mask, n=32 | 32 | 9.1e-07 | 9.5e-07 | 9.2e-07 |
| softmax+CE dlogits, 8×16 | 128 | 9.1e-05 | 2.2e-03 | 7.7e-05 |
| softmax+CE dlogits, 64×16 | 1024 | 8.3e-05 | 3.4e-03 | 8.9e-05 |

All elements pass the standard combined criterion `|err| <= 1e-3·|g| + 1e-4`
(0 over-tolerance).  The few per-element relative errors above 1e-3 are on
gradients of magnitude ~0.01, where the finite-difference noise floor is
~1e-5 absolute: the softmax loss is evaluated in fp32 with a relative error of
~3e-7 on a loss of ~3, which is 1e-6 absolute, divided by 2h = 0.04.  The
global relative error, which is what the per-layer gradients see, is 8e-5.

The softmax kernel's own accuracy against the CPU oracle (not FD):
dlogits max abs 5.2e-9 (64×16), 1.3e-9 (512×16 with −1e30 padding columns);
total loss relative 2.2e-7 and 3.3e-7; argmax count exact.

## Toy trainer

`tests/test_train.c`: 64-32-10 MLP, bias folded into augmented weight rows
(row 64 of W1, row 32 of W2; the six padding output columns are biased to
−1e30 so the 16-wide softmax kernel ignores them).  Dataset: 10 Gaussian
clusters in 64 dimensions (deterministic xorshift seed 12345, noise 0.35),
640 train / 160 test samples generated on the host and uploaded once.  Full
batch, 300 steps, loss/accuracy totals reduced by a GPU GEMM (onesᵀ·partial).

Loss falls 2.3 → 9.3e-4 (SGD, 2480×) and 2.3 → 3.0e-5 (Adam, 78 000×); the
printed points are monotone.  Both optimizers also match a CPU oracle after
one step (worst relative 6.9e-8 / 8.1e-8, including m and v).

Reproducibility: the trainer was run twice per optimizer in separate
processes; the logs (loss, accuracy, gradchecks, op counts) are byte-identical
after removing the timing line.  The gradient checks and the primitive tests
were likewise run twice with identical output.

## Op coverage delta

Before: 8 of 22 registry entries dispatchable.  After: **15 of 27**.
Added: `relu_bwd`, `rsqrt`, `transpose`, `matmul_bt`, `softmax_ce_bwd`,
`softmax` (and `transpose/permute` flipped to supported, restricted to a
dense 2-D transpose).  Still unsupported, honestly listed: `conv2d/5x5`,
`conv2d/stride2`, `conv2d/depthwise`, `conv2d/grouped`, `matmul/f16`,
`matmul/f32x4-tile`, `batched-matmul`, `maxpool`, `layernorm`, `concat/slice`,
arbitrary `permute`, `upsample`, `quantize/dequantize`.

The existing suite is still green on the new tree: `REPS=1 ./run_tests.sh`
builds everything and passes add/mul/relu/tail/sigmoid/silu (bit-exact where
required), matmul 8.46 GFLOP/s at 256³ (baseline 8.49), all six conv shapes,
strict dispatch, then the new training tests; `ALL TESTS PASSED`, board LIVE
after every stage.

## Honest limits

- **fp32 only, no FMA**, and the FPU truncates.  Everything above is within
  ~1e-6 relative; the argmax test in the softmax kernel is an **absolute
  1e-5 tolerance** because the hardware vector-rotate primitive returns a
  value with its low byte perturbed (measured 2.50054908 → 2.50054741).  This
  is the one place where a "gradient check" number is not exact equality of a
  comparison; it is documented in `docs/NUMERICS.md`.
- **Fixed 16-wide softmax rows.**  The fused kernel handles exactly 16 padded
  columns per row (the toy uses 10 + 6).  A 32/64-class model needs a second
  reduction pass; not written.
- **Memory.**  One 64 MiB dma-buf arena (the docs assume up to 76 MiB); no
  checkpointing, no micro-batch accumulation, no model sharding.  The toy uses
  < 4 MiB, so the limit is not exercised here.
- **No conv backward.**  The im2col path has no gradient kernel, so the
  "small conv net" toy from the roadmap is not built.  The op set for training
  is therefore linear/relu/softmax-CE only.
- **Host work is layout only**: padded/zero-filled panels, the Ha row copy
  (32 floats per row), hyperparameter scalar buffers and the accuracy display
  division.  No MAC, no reduction, no activation and no optimizer arithmetic
  runs on the ARM.
- **The softmax kernel is launch-bound** (one 8-row group per QPU per launch,
  no loop; a looped version hung the V3D once and was abandoned).  Steps/s is
  dominated by ~25–40 launches per training step, not by FLOPs; bigger
  batches per launch are the obvious next speed step.
- **Clock.**  Sustained GPU load droops 400 → 250–275 MHz.  The trainer
  numbers above were taken with the sampler reading 400 MHz; a whole-suite
  stress run sits at 250–275 MHz and the trainer then measured 105 steps/s
  (SGD), i.e. the launch-bound rate barely moves.

## Run it

```sh
cd ~/work/train
make
sudo ./build/test_train_ops
sudo ./build/test_grad 1
sudo ./build/test_train --opt sgd  --steps 300
sudo ./build/test_train --opt adam --steps 300
REPS=1 ./run_tests.sh          # everything, serialised + board checks
```
