# vc4d — a privileged helper daemon for the VideoCore IV QPU

`vc4d` moves the only privileged part of the `libvc4infer` engine — mapping
`/dev/mem` for the V3D register block and for the physical base of the dma-buf
arena — into one small root daemon.  Unprivileged clients (group `vc4`) then
allocate GPU-visible buffers, upload QPU programs, launch them and read results
over a unix socket.  They never open `/dev/mem` and never hold a capability.

The demo is the verified asm10 256×256×256 GEMM, run as user `raspi` entirely
through the daemon and checked element by element against a double-precision
oracle: **0 mismatches in 3/3 runs**, with **exactly the same V3D execution
cycle count** (6 773 184) as the direct root path.

```
 build 13 GEMM 256^3 through vc4d      13.7 GFLOP/s kernel, ~7.2 GFLOP/s measured on
                                       this board state, 0/65536 mismatches
```

## 2. Protocol

**Transport.** `AF_UNIX` / `SOCK_SEQPACKET` at `/run/vc4d.sock`, mode `0660`,
group `vc4`, owner root.  No TCP, no abstract namespace, no other family.
`SO_PEERCRED` is read on accept and used in every log line.  SCM_RIGHTS is
used *only* by the daemon (ALLOC replies); a client that attaches a file
descriptor to any request is refused and the descriptor is closed.

**Framing.**  Every message starts with a 28-byte header.  `hdr.len` is the
total message length and must equal the datagram size; the size is capped at
64 KiB.  All integers are little-endian host order (same machine).

```c
struct vc4d_hdr {
    uint32_t magic;    /* 0x44344356 "VC4D" */
    uint32_t len;      /* header + payload, must equal the datagram size */
    uint16_t op;
    uint16_t version;  /* 1 */
    uint32_t seq;      /* echoed in the reply */
    int32_t  status;   /* request: 0; reply: VC4D_* */
    uint32_t detail0;  /* reply: op-specific (e.g. previous register value) */
    uint32_t detail1;
} __attribute__((packed));
```

A reply always echoes magic/op/version/seq.  One request is outstanding per
connection (the client library is synchronous).

| op | name | request payload | reply payload |
|---|---|---|---|
| 1 | `HELLO` | `{version, flags}` | `{version, arena_bytes, data_base, page_size, max_msg, max_qpu, max_uni, max_prog, flags, ident0, ident1, ...}` |
| 2 | `ALLOC` | `{bytes, flags}` | `{handle, off, len, bus}` **+ dma-buf fd via SCM_RIGHTS** (`bus` = GPU bus address of the region) |
| 3 | `FREE` | `{handle}` | — |
| 4 | `UPLOAD` | `{bytes, max_qpu, nuni, flags}` + program bytes [+ name bytes with `VC4D_UPLOAD_NAMED`] | `{prog, code_off, words}` |
| 5 | `LAUNCH` | `{prog, timeout_ms, nqpu, nuni, flags, uni_handle, uni_off, uni_addr}` + `nqpu*nuni` entries, or none with `UNI_IN_ARENA` | `{launch, nqpu}`, or `{launch, errs, wall_ns, cycles}` with `WAIT` |
| 6 | `WAIT` | — | `{launch, errs, wall_ns, cycles}` |
| 7 | `READ_REGS` | `{off, count}` | `count == 0`: `struct vc4d_regs` snapshot; else `{off,count}` + `count` words |
| 8 | `WRITEREG` | `{off, val}` | `detail0` = previous value |
| 9 | `STATS` | — | `{launches, launches_failed, bytes_uploaded, reg_writes, rejects, arena_bytes, arena_used, gpu_ns, clients, max_clients, programs, dead}` |
| 10 | `SYNC` | `{handle, dir}` | — |
| 11 | `CLOSE` | — | — |
| 12 | `PING` | — | `detail0 = 1` |

**Uniform entries** (16 bytes each, QPU-major: `nqpu × nuni`):

```c
struct vc4d_uni {
    uint32_t kind;    /* 0 = literal, 1 = pointer */
    uint32_t handle;  /* buffer handle (pointer) or 0 (literal) */
    uint32_t off;     /* literal value, or byte offset inside the buffer */
    uint32_t len;     /* bytes the program will touch, or 0 (literal) */
};
```

* `UNI_PTR`: the daemon resolves `arena_bus + buffer.off + off` after checking
  `off % 4 == 0`, `len % 4 == 0`, `len > 0` and `off + len ≤ buffer.len`
  (in 64-bit arithmetic, so an overflow offset cannot wrap).  The buffer
  handle must belong to the calling client.
* `UNI_LIT`: `handle` and `len` must be zero; the value is written verbatim
  **unless** it falls in the GPU bus window (`≥ 0xC0000000`), the V3D MMIO
  window (`0x3FC00000..0x3FC03FFF`) or the arena's physical range — those are
  refused (`E_DENIED`) because a legitimate kernel gets every address through
  a `UNI_PTR` entry.

`UPLOAD` declares how many uniform words the program consumes (`nuni`), and
`LAUNCH` must supply exactly that many — a program can never be started on a
short uniform block and read stale words.

**UNI_IN_ARENA** (`LAUNCH.flags & VC4D_LAUNCH_UNI_ARENA`): the caller has
already materialised the uniform words in its own mapped region.  The request
ends after the 32-byte `vc4d_launch_req`; `uni_handle` names the region,
`uni_off` is the 64-byte-aligned first QPU block, and QPU *q* reads
`[uni_off+64q, +64)`.  The daemon checks the region belongs to the caller,
`uni_off % 64 == 0`, `uni_off + 64*nqpu ≤ region.len`, then validates the words
and points `SRQUA` straight at the block.  Containment is per-arena instead of
per-buffer; `UNI_PTR` stays the stricter interface.  A program can only read
words up to its declared `nuni`, so the tail of the 64-byte block is not a way
around the check.

**UNI_MASK** (`flags & VC4D_LAUNCH_UNI_MASK`, 1.2.7): `vc4d_launch_req.uni_addr`
(a field that used to be `pad`, so the message size is unchanged) is a bitmask
over the uniform slots: bit *u* set means "word *u* is a GPU bus address this
program consumes".  Each declared address must lie inside the caller's arena;
a word whose bit is clear is a **value** and is not compared with any address
window, which is what makes `-2.0f` (`0xC0000000`), `-3.0f` (`0xC0400000`),
`-inf` and every other float ≤ −2.0 usable as a parameter.  Bits ≥ `nuni` must
be zero.  A launch that sends no flag keeps the older rule ("inside this arena,
or a literal outside the bus/arena/MMIO windows"), so 1.2.6 clients are
unaffected.  The engine sets the mask on every launch: a word is declared an
address exactly when it points into the client's arena.

The mask is a correctness aid, not a security boundary.  A client that marks a
real address as a value can already make the QPU read anywhere by putting the
address in the instruction stream (§3, "What it cannot do"); what the mask
removes is the daemon's inability to tell a *legitimate* float from an address.

**Named programs** (`UPLOAD.flags & VC4D_UPLOAD_NAMED`, 1.2.7): the payload is
`vc4d_upload_req + code + name`, name 1..63 printable bytes, no NUL.  The name
keys the program-slot LRU: re-uploading a name reuses its slot, and when all
127 client slots are in use the least recently used one that is not executing
is freed (the daemon's probe slot and the in-flight program are never
evicted).  A client that sends no name is keyed by the code's SHA-256, which
behaves the same for repeated uploads.  `STATS.evictions` counts the frees;
`--verbose` logs each one with the name.

**LAUNCH_WAIT** (`flags & VC4D_LAUNCH_WAIT`): kick, poll to idle, record the
counters and L2 write-back, all in one round trip.  The reply is
`struct vc4d_wait_rsp` instead of `vc4d_launch_rsp`; no `WAIT` follows.  This
is what the engine uses (`UNI_IN_ARENA | WAIT`), so a kernel costs one
message.  The poll interval is 10 µs.

**ALLOC** also returns `bus`, the GPU bus address of the region's first byte;
a client that builds pointer uniforms itself needs it.

**Status codes:** `OK`, `E_PROTO`, `E_VERSION`, `E_TOOLARGE`, `E_INVAL`,
`E_NOMEM`, `E_NOENT`, `E_BUSY`, `E_TIMEOUT`, `E_GPU`, `E_DENIED`, `E_IO`,
`E_DEAD`.

**Example — one GEMM iteration** (what `demo_gemm` does):

```
HELLO                       -> arena size, V3D ident
ALLOC(262144, ZERO)  x4     -> 4 region handles + one fd each; mmap(fd, off, len)
memcpy A,B into the mappings; SYNC(A,W2G), SYNC(B,W2G)
UPLOAD(pack10_256.bin, nqpu_max=4, nuni=8)  -> prog p1
UPLOAD(gemm10_256_..._q12.bin, 12, 8)       -> prog p2
LAUNCH(p1, nqpu=4, 8 uniforms x 4 QPUs)     -> launch id
WAIT                                        -> 0.52 ms, cycles
LAUNCH(p2, nqpu=12, 8 uniforms x 12 QPUs)   -> launch id
WAIT                                        -> 4.15 ms, cycles
SYNC(C, G2R)
```

## 3. Security model

### What the daemon holds, and when

Only during startup: `/dev/mem` (twice), `/dev/dma_heap/linux,cma`, `/dev/vcio`
(one firmware `ENABLE_QPU` mailbox call).  It maps the V3D block and the arena,
then **closes those descriptors** and drops privileges:

```
Uid:  65534 65534 65534 65534
Gid:  65534 65534 65534 65534
CapEff: 0000000000000000
NoNewPrivs: 1
fds: 0 /dev/null, 1-2 journal, 3 socket, 4 /dmabuf:, 5 /tmp/vc4-gpu.lock
```

So after startup there is no path back to `/dev/mem`, no capability, and the
process is not dumpable.  It never `exec`s, never loads code, and its only
listener is the unix socket.

### What it enforces

| check | where |
|---|---|
| message magic, version, `len == datagram size`, status must be 0 | `vc4d.c` main loop |
| 64 KiB cap, truncation/`MSG_TRUNC`/`MSG_CTRUNC` | `vc4d.c` |
| any client-supplied fd is closed and the request refused | `vc4d.c` |
| per-op exact payload size | every `handle_*` |
| region handle ownership, `off+len` inside the region, 4-byte alignment | `handle_launch` |
| literal uniforms may not be bus/arena/MMIO addresses | `literal_forbidden` |
| with `UNI_MASK`, declared addresses must be inside the arena; value words are not compared with address windows | `arena_addr_ok`, `handle_launch` |
| program slots: LRU keyed by name, probe and in-flight never evicted | `prog_slot_for` |
| the arena is retried, then degraded loudly, and restored when idle | `arena_open`, `arena_maybe_restore` |
| `nqpu ≤ declared max_qpu`, `nuni == declared nuni` | `handle_launch` |
| one launch in flight; `WAIT` only by the owner | `handle_launch`/`wait` |
| timeout bounded by `--max-timeout-ms`; then a context reset that must pass a probe launch, or the daemon exits 75 | `try_recover`, `gpu_recover` |
| a client's regions are released when its **peer pid** is gone, not only when its socket closes | `peer_alive`, `reap_dead_clients` |
| register writes only to the allowlist | `gpu_wreg` |
| program SHA-256 allowlist in `--strict` | `handle_upload` |
| arena physical base verified against `/dev/mem` before first use | `verify_phys` |
| denial logging (rate-limited), `SO_PEERCRED` on every line | `log_denial` |
| bounded GPU-lock wait, disconnect-mid-launch cleanup | `gpu_lock_take`, `client_destroy` |

Register write allowlist: `SRQPC`, `SRQUA`, `SRQUL`, `SRQCS`, `VPMBASE`,
`L2CACTL`, `SLCACTL`, `VPACNTL`, `INTCTL`, `INTENA`, `INTDIS`.  Reads are
unrestricted (a read cannot change state) and `READ_REGS` can dump the whole
4 KiB block.  In `--strict` mode the raw SRQ/VPMBASE writes are refused too, so
the only way to start the QPU is `LAUNCH` with an allowlisted program.

### What it cannot do

**A QPU program is raw machine code, and a QPU can DMA anywhere in the 32-bit
bus space.**  The daemon validates every *declared* pointer, but it does not
disassemble the program, so a deliberately hostile client can compute an
address inside the program (e.g. from an immediate in the instruction stream)
and read or write physical memory.  This is inherent in exposing raw QPU
programming; the structural checks stop accidents and naive attacks, not a
determined attacker who is allowed to upload arbitrary code.

The mitigation is `--strict`:

* every program must hash to a line in `/etc/vc4d/programs.sha256`;
* raw `SRQ*`/`VPMBASE` writes are refused;
* the timeout defaults to 2 s.

With `--strict` the daemon can only ever run the kernels you shipped, which is
the right profile for an appliance.

Other honest limitations:

* **The `vc4` group is a mutual-trust group.**  All clients share one arena,
  and an `ALLOC` fd can be mapped over the whole arena (it is the same dma-buf),
  so client A can scribble on client B's buffers.  Handles are per-client and
  checked, but memory isolation between clients would need one dma-buf per
  client (easy to add; not done because CMA is the scarce resource).
* **A bad kernel can still hang the GPU** (and historically the whole board).
  The daemon bounds it with a timeout and then resets the V3D context and
  verifies it with a launch of its own 4-instruction probe program (see
  §4.3); if the reset cannot be verified it exits so systemd starts a clean
  one.  A really wild kernel can still reboot the Pi.  One GPU user at a time
  remains the operational rule.
* `WAIT` polls the queue inside the single-threaded loop, so one slow launch
  delays other clients by at most the timeout.
* The physical-base scan reads 1008 × 4 KiB from `/dev/mem` (~5 ms measured);
  it then verifies the result from three different offsets before trusting it.

```sh
sudo /usr/local/sbin/vc4d --strict --allowlist /etc/vc4d/programs.sha256 ...
```

```sh

ls -l /run/vc4d.sock                      # srw-rw---- root vc4
sudo grep -E '^(Uid|CapEff|NoNewPrivs):' /proc/$(pgrep -x vc4d)/status
```

## 5. Measurements (Pi 3B, stock clocks: core 400 MHz, V3D 300 MHz, ARM 1.2 GHz)

`get_throttled` reads `0x20000` (the sticky "soft temperature limit has
occurred" bit, set by an earlier development hang) — it is not an active
throttle and the clocks above are the stock values all the way through.

256×256×256 f32 GEMM, both paths, same boot, 5 reps each, best-of reported.
`gpu ms` is pack+GEMM time; `cycles` is the V3D execution-cycle counter the
engine reads after each launch.

| path | gpu ms | GFLOP/s | wall ms (client) | wall overhead | V3D cycles |
|---|---:|---:|---:|---:|---:|
| direct root (`libvc4infer`, `/dev/mem` in-process) | 4.28 | **7.84** | 4.30 | 0.01 ms | 6 773 184 |
| through `vc4d` (unprivileged, 6 round trips) | 4.43 | 7.58 | 4.66 | **0.24–0.42 ms** | **6 773 184** |

Across repeated sessions on this boot the same two binaries measured
4.28–4.52 ms / 7.42–7.84 GFLOP/s (direct) and 4.43–4.72 ms / 7.13–7.58 GFLOP/s
(daemon), with 0.24–0.63 ms of wall overhead (5–13 %).  That spread is
board/DRAM noise at stock clocks; the comparison that does not move is the V3D
cycle counter.

* The kernel work is identical — the cycle counter is bit-for-bit the same
  (38 752 pack + 6 734 432 GEMM) — so the wall difference is protocol, not
  compute.
* Per-message round trip: **43–60 µs** (200 PINGs).  A GEMM iteration makes
  6 round trips (2 SYNC, 2 LAUNCH, 2 WAIT) ≈ 0.3–0.4 ms plus client-side
  `memset`/cache maintenance ⇒ **0.24–0.63 ms, 5–13 % of wall**.
* `throttled=0x0` at the start of the run; the sticky soft-temperature bit
  (`0x20000`) that appears later was set by an earlier development hang, not by
  the delivered code.

## 6. Test results

`tools/run_acceptance.sh` → **ACCEPTANCE PASSED**

* `demo_gemm --reps 3`: **3/3 clean, 0/65 536 mismatches per run**

* Daemon evidence: uid 65534, `CapEff=0`, `NoNewPrivs=1`, no `/dev/mem` fd,

* `test_hostile`: **82/82 passed**, including
  * 23 truncation lengths, bad magic/version/len/status, unknown opcode;
  * 70 KiB and 2 MiB datagrams (over the 64 KiB cap);
  * ALLOC 0 / 4 GiB / bad flags / trailing bytes; FREE double-free;
  * UPLOAD 0 / unaligned / 20 KiB / lying length / `max_qpu=99` /
    unexpected SCM_RIGHTS fd;
  * LAUNCH with out-of-range `off+len`, one-page-past-the-end, overflow
    offset, zero length, unaligned offset, bogus handle, literal bus address,
    literal MMIO address, unknown kind, `nuni != declared`;
  * second LAUNCH while one is in flight (`E_BUSY`), WAIT with no launch;
  * READ_REGS out of range/oversized/unaligned + whole-block dump;
  * WRITEREG not-allowlisted / outside block / unaligned / allowlisted;
  * 2000 random fuzz datagrams, then PING and STATS;
  * a client that launches and disconnects without WAIT;
  * a second client that tries to launch the first client's program or point
    a uniform at its buffer (both `E_NOENT` — per-client ownership);
  * strict-mode allowlist rejecting a one-byte-modified program.
* All of the above leave the daemon running (`dead=0`) and the V3D `LIVE`.

The earlier development crash (a uniform *address* vs *value* mix-up in
`SRQUA`) is what motivated: the arena physical-base verification, the
`nuni`-declared-at-UPLOAD rule, and the `--strict` allowlist.

### 6.1 Recovery and reclaim (the two regressions that turned a failure permanent)

**A launch timeout no longer kills the daemon (was G1).**  `gpu_abort()` still
clears the queue word and sets `dead`, but `try_recover()` then resets the
context under the board GPU lock and *proves* it:

1. wait up to 1 s for `SRQCS` to read idle (a launch that missed its deadline
   can still be draining);
2. write back + invalidate L2, invalidate the slice caches, W1C `ERRSTAT`,
   `VPMBASE=16`, re-arm the counters, `SRQ` reset, and require an idle queue;
3. launch the daemon's own probe program - four instructions,
   `thrend` + the three delay slots every kernel ends with - from the reserved
   last code slot (`PROBE_SLOT = 127`), with a zeroed 64-byte uniform block,
   and require completion with no new `ERRSTAT` bits.

Measured on this board: 12 cycles, ~1 us per probe, sub-millisecond for the
whole reset.  If any step fails (queue will not drain, V3D powered down, probe
incomplete) the daemon logs `GPU context reset FAILED: …` and **exits 75**;
`Restart=always` starts a clean one in ~2 s.  Either way no zombie.

The register *mapping* is not re-created, and cannot be: it is a `MAP_SHARED`
`/dev/mem` mapping of the V3D window that stays valid for the process's life,
and re-mmap would need `CAP_SYS_RAWIO` + `/dev/mem`, both given up before
serving clients.  What is re-initialised is the register *state*, and the probe
is what makes that checkable instead of assumed.

**A departed client's arena comes back (was G9).**  Reclamation used to be
tied to the socket: if a client forked (or leaked its descriptor) and the
allocating process exited, its region stayed pinned until the *socket* closed -
measured: one 8 MiB region outlived its owner and the next client was denied
`op=ALLOC: arena exhausted` while nothing was running.  Liveness is now
anchored on the peer pid from `SO_PEERCRED` (`kill(pid, 0)`: `ESRCH` = gone,
`EPERM` = alive), checked every poll iteration, on `HELLO`, and before
refusing a connection for lack of a slot.  The heap is a page bitmap instead of
a capped free list, so a freed page cannot be lost either.  Trade-off: a client
that forks and keeps *using* the inherited connection after the parent exits is
reaped - it must reconnect.

## 7. The engine on vc4d (`VC4INFER_DAEMON=1`)

The port is in place in `/home/raspi/work/train-conv` (and the copy in
`vc4-stack/engine`).  `VC4INFER_DAEMON=1` selects the unprivileged backend;
unset or `0` keeps the direct `/dev/mem` path, unchanged.

**What was added to the engine** (the op code — `vc4_gemm.c`, `vc4_ew.c`,
`vc4_conv.c`, `vc4_convbwd.c`, `vc4_train.c` — is untouched apart from cache
dirty marks at four CPU-write sites):

| file | purpose |
|---|---|
| `src/vc4_dev_remote.c` | connect, ALLOC + mmap, UPLOAD on first use, one-round-trip LAUNCH_WAIT, dirty-range cache maintenance |
| `src/vc4_dev.c` | backend dispatch at `vc4_init`, `vc4__launch`, `vc4_upload`, `vc4_download`, `vc4__l2_flush`, `vc4__write`, `vc4_shutdown`, `vc4__wait_idle`, `vc4__health`, `vc4__kernel_load_file` |
| `tests/bench_matmul.c` | the same binary measures both paths (`RESULT ... vc4d` / `direct`) |
| `run_tests.sh` | `VC4INFER_DAEMON=1` runs the suite as the invoking user (no sudo) and prints `/proc/PID/fd` + `CapEff` evidence |

**Protocol version 2** adds exactly what the port needed:

* `ALLOC` replies with `bus`, the GPU bus address of the region, so the client
  can build pointer uniforms without knowing the arena base.
* `LAUNCH.flags & VC4D_LAUNCH_UNI_ARENA`: the uniform words are already
  materialised in the caller's own mapped region.  `uni_handle` names the
  region and `uni_off` the 64-byte-aligned first QPU block; QPU *q* reads
  `[uni_off+64q, +64)`.  The daemon validates every declared word as "a bus
  address inside this arena" or "a literal outside the bus/arena/MMIO
  windows" and points `SRQUA` at the block.  **No op-code changes**: the
  engine already writes uniforms through `vc4__uni()` into the arena.
  Containment is per-arena instead of per-buffer; the `UNI_PTR` mode remains
  the stricter interface for clients that can tag their uniforms.
* `LAUNCH.flags & VC4D_LAUNCH_WAIT`: kick, poll to idle, finish and L2
  write-back in **one** round trip; the reply is `struct vc4d_wait_rsp`.
  The engine uses `UNI_IN_ARENA | LAUNCH_WAIT`, so a kernel costs one message.
  `handle_launch` and `handle_wait` share `await_launch()`, and the poll
  interval is 10 µs instead of 50 µs.

**Coherency — a correction to the earlier note.**  The CMA dma-buf mapping is
**cacheable** on this kernel, not write-combining: the daemon's uncached
`/dev/mem` read of a freshly-written uniform block returned all zeros until the
client did `dc civac`.  (The demo always called `vc4c_sync()`, so it never
noticed.)  The remote backend therefore tracks CPU-dirtied byte ranges —
`vc4_upload`, `vc4__write`, the uniform blocks, the per-op scratch high-water,
and the four persistent output copies — and cleans exactly those ranges before
each launch; `vc4_download` and `vc4__l2_flush` clean+invalidate the ranges the
CPU is about to read (safe because every line is cleaned before a launch, so a
later CIVAC cannot write a stale line back over a GPU result).  This matters
for performance: a full 62 MiB clean would cost milliseconds, while a 256³
matmul dirties ~1.5 MiB.

**Timing note.**  The daemon takes `/tmp/vc4-gpu.lock` for each launch, so the
client tests do not hold it in daemon mode (`tests/util.h` returns a dummy fd);
otherwise the two `flock`s deadlock.  If another user already holds the lock,
`LAUNCH` returns `E_BUSY` without kicking anything; the engine retries for up
to a minute so a concurrent direct-root run is survived.  `ReadWritePaths`
in the unit now includes `/tmp` so the daemon can create the lock at boot.
Since the G11 fix the *engine* also takes this lock per launch in direct mode,
so a direct run and a live daemon take turns instead of overwriting each
other's queue; a wrapper must therefore not take the lock itself (the engine
detects the resulting wait and fails with a message naming the lock after
`VC4INFER_GPU_LOCK_MS`, default 30 s).

**Sizing.**  The unit starts with `--arena-mb 72` (CMA is 256 MiB on this
board).  The engine's default client arena is 64 MiB and the daemon's data
heap starts at 2 MiB, so a 64 MiB daemon arena left a client 1 MiB short and
`test_convgrad` failed late with `E_NOMEM`; 72 MiB gives the client its full
64 MiB region.  A 128 MiB arena also works when it can be allocated, but a
128 MiB contiguous CMA block is not reliable at boot: the daemon's own shrink
ladder fell back to 64 MiB after the vc4 DRM driver and fragmentation had
taken the rest, which reproduced the failure.  72 MiB has been reliable
across restarts.  `MAX_PROGS_CLI` is 64 (from 16):
the engine uploads one program per kernel *shape*, and a single conv-grad
process legitimately needs ~25, so a 16-slot per-client cap made later
gradient kernels fail to upload.

**Acceptance**: `REPS=5 VC4INFER_DAEMON=1 ./run_tests.sh` as user `raspi`
passes the whole suite with 0 mismatches (matmul all shapes, conv 3×3/1×1,
elementwise, training ops, finite-difference grad checks, MLP and conv-net
training).  The client process has uid 1000, `CapEff=0`, and fds
`0,1,2,3->/dev/null,4->socket` — **no `/dev/mem`**.  The daemon still runs as
`nobody`, `CapEff=0`, `NoNewPrivs=1`.

Measurements and the full evidence are in `vc4-stack/docs/DAEMON.md`; the
short version (Pi 3B, stock clocks: core 400 MHz, V3D 300 MHz, same boot, 5
reps, best wall):

| size | path | gpu ms | gpu GFLOP/s | wall ms | wall GFLOP/s | wall overhead |
|---|---|---:|---:|---:|---:|---:|
| 256³ | direct root | 3.962 | 8.47 | 3.980 | 8.43 | — |
| 256³ | through vc4d | 3.998 | 8.39 | 4.289 | 7.82 | **+0.309 ms (7.8%)** |
| 128³ | direct root | 0.706 | 5.94 | 0.723 | 5.80 | — |
| 128³ | through vc4d | 0.771 | 5.44 | 0.942 | 4.45 | **+0.219 ms (30%)** |

Both paths ran the same `bench_matmul` binary in the same boot, five reps,
best.  The QPU work is within 1% at 256³; the wall difference is two round
trips (~50 µs each) plus one dirty-range clean (~1.5 MiB at 256³).  At 128³ the
same fixed cost is 30% of a 0.72 ms call — launch-bound, not compute-bound —
so the 15% target is met at 256³, the size the engine is used at.  This is
better than the demo's 5–13% because the engine uses one `LAUNCH_WAIT` round
trip per kernel instead of six messages per GEMM iteration.

## 8. Notes for the next person

* `DC IVAC` (invalidate by VA without writeback) is **undefined at EL0** on
  ARMv8 — it traps as `SIGILL`.  GNU as 2.44 still assembles `dc ivac` happily
  (as an `op1=0` encoding) and `sys #3,c7,c6,#1` traps too.  Userspace must use
  `dc civac`; `libvc4client` does.
* `/dev/mem` writes go through a cacheable kernel alias, so `pwrite`+`pread`
  self-tests of the arena can lie.  `verify_phys()` therefore writes through
  the uncached mapping and reads back a *page* at three offsets.
* `fs.protected_regular` refuses `O_CREAT` on a `/tmp` file owned by another
  user, which breaks `flock(1)` across users; both the daemon and
  `bench_direct` fall back to `O_RDONLY` before `flock`.
* The QPU queue reports completion with `SRQCS done == nqpu && queue == 0`;
  a timeout cannot be recovered from the ARM, which is why the daemon goes
  permanently dead instead of retrying.
* The dma-buf mapping from `linux,cma` is cacheable on this kernel (measured;
  see §7): `vc4c_sync()` is required before a launch and after one, not
  defensive.  Reads are still slow compared with cached memory (the daemon
  reads the same pages uncached), so a CPU read of a result should be one
  streaming pass (as `demo_gemm` does), not random access.
* `vc4d.service` needed `ReadWritePaths=/tmp` in addition to `/run`: with
  `ProtectSystem=strict` the daemon could not create `/tmp/vc4-gpu.lock` at
  boot, so it started without the interop lock.
